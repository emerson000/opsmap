# Vikunja sync

Optional two-way sync with [Vikunja](https://vikunja.io). Set `VIKUNJA_URL` (the Vikunja origin) to turn it on; without it `/tasks` (and its Vikunja alias `/vk`) is hidden and nothing syncs. The server only ever talks to that origin.

Each user connects their own Vikunja account in the app (stored per user and per task service; the API is `GET`, `PUT` and `DELETE /api/tasksync/vikunja/account`): user menu (phone: menu) → **Vikunja…**, paste an API token made in Vikunja under Settings → API Tokens (projects, tasks, buckets and webhooks). The server checks it with Vikunja (`GET /user`) before saving and never sends it back; the panel shows only the Vikunja user name. Tokens are encrypted at rest with AES-256-GCM and bound to their user. The 32-byte key is read from `OPSMAP_SECRET_KEY_FILE` (64 hex characters), or created at `DATA_DIR/secrets/master.key` (0600) when unset. The key is not in `opsmap.db` or its nightly backups. Keep it with your backups separately, or a restored database will need everyone to paste their token again. A map syncs with the token of the user who bound it; if that user removes their token, `/vk status` says so and syncing stops until they reconnect.

- `/tasks bind "Project"` (or `/vk bind "Project"`; `/tasks bind vikunja "Project"` when the server has more than one task service) binds the open map (the A/O) to a Vikunja project, found by title or created. Each sector becomes a child project with the sector's name (found or created, and created later for sectors added afterwards). Units of kind unit and event become tasks in their sector's project. Persons and places stay on the map, and units already done or dropped are not created. Open tasks already in those projects, and tasks made in Vikunja later, arrive as **pending** units in that sector.
- Synced both ways: title; due date (compared by calendar day in the map's zone); note ↔ description (plain text; HTML from Vikunja is stripped); BDA ↔ progress for hostiles and suspects (60% done = 40% strength; a friendly's strength is capacity, so it is not synced); sector ↔ project (moving a task to another sector project moves the unit); state ↔ kanban bucket: To-Do = todo, Doing = active, Blocked = blocked (bind adds the bucket), Done = done. A task done in Vikunja runs `/done` (a hostile is destroyed); reopening it runs `/reopen`. Tasks in buckets of your own keep their unit's state. A task deleted in Vikunja drops its unit, and a unit dropped in opsmap marks its task done. A task that still exists is never treated as deleted: moved to a project outside the A/O (or left in a removed or archived sector's project), it goes back to its unit's sector. Binding links an open, unlinked task with the same title in the same sector project instead of creating a second one, so unbinding and binding again does not duplicate anything. One task or unit that fails (a Vikunja error) does not stop the others; `/vk sync` and `/vk status` name it.
- Relations ↔ task forces and links, between units that both have a task:
  - A unit attached to a task force (`/attach`, `/reinforce … with`) is a subtask of the task force's task: its task's parent task. A subtask added in Vikunja (from either task) runs `/attach`; removing it runs `/detach`. A unit has one task force, so a task with several parent tasks keeps its unit's task force until you remove the extra ones. Parent tasks outside the A/O are left alone.
  - `/link A B` is "related", `/link A B as dependency` is "A is blocked by B" (B is blocking A), and `/link A B as handoff` is "A precedes B" (B follows A). A relation of one of these kinds added in Vikunja runs `/link`; removing it there cancels the link order. Cancelling the order in opsmap (`/halt`) removes the relation. A relation opsmap cannot take, such as one between units in different sectors where neither is a task force, is reported once by `/vk sync` and left in Vikunja.
  - Links sync only while both units are open: `/done` and `/drop` end a unit's link orders, but its task keeps its relations. Other kinds (duplicate of, copied from) and relations to tasks outside the A/O are not synced.
- Identity ↔ labels: each task carries one identity label, `hostile`, `suspect`, `friendly`, `assumed`, `neutral`, `unknown` or `pending` (`enemy` and `friend` are read too). Labels are matched by title ignoring case and created, colored like the frames, on first use; other labels are left alone. Setting one in Vikunja runs `/id`; `/id` swaps the label. A task with no identity label gets its unit's; one with several keeps opsmap's identity and loses the extras. A task made in Vikunja with an identity label arrives with that identity instead of pending.

Each field merges three ways against the values both sides last agreed on: changed on one side, it is copied across; changed on both, the newer change wins. Changes from Vikunja are logged as `VIKUNJA: …` by the system with via `vikunja`.
- opsmap pushes about a second after each change. Vikunja changes arrive through webhooks that opsmap manages itself: one per sector project (`task.created`, `task.updated`, `task.deleted`, `task.relation.created`, `task.relation.deleted`) posting to `PUBLIC_URL/api/vikunja/hook/<map>` (the server also accepts the generic `PUBLIC_URL/api/tasksync/vikunja/hook/<map>`), signed with a per-map secret (HMAC-SHA256 in `X-Vikunja-Signature`; unsigned or wrongly signed deliveries get 401). Bind registers them. They are checked every 10 minutes and at once on `/vk sync` or a sector change, and a webhook deleted or altered in Vikunja is made again. Unbinding or deleting the map removes them. `/vk status` shows how many are registered and the last delivery. Webhooks need `PUBLIC_URL` to be an address Vikunja can reach (not loopback), and Vikunja refuses private addresses, tailnet ones included, unless it runs with `VIKUNJA_OUTGOINGREQUESTS_ALLOWNONROUTABLEIPS=true`. The server also polls: every minute, or every 5 minutes while webhooks are being delivered.
- `/vk status` reports the binding and the last sync or error, `/vk sync` syncs now, `/vk unbind` stops syncing (tasks stay in Vikunja; its webhooks are removed). The bind is recorded by the system, so `/undo` does not reverse it; `/vk unbind` does. Who bound a map is kept on the server, not in the map document: an imported or new map never carries a binding (export, import and duplicate drop it), so no document can make the server use someone's token. The inspector links each synced unit to its task. MCP `opsmap_command` takes the same `/tasks` and `/vk` text.
- A map has one binding. `/tasks sync` or `/tasks status` on an unbound map answers `This map is not bound to a task service: /tasks bind "‹project›"`, and binding a bound map to another project answers `Bound to Vikunja project ‹title›: /tasks unbind first`. `/vk status`, `/vk sync` and `/vk unbind` work the same as the `/tasks` forms. An alias names its service: on a map bound to another service, `/asana unbind` (or `sync`, `status`) answers the same `Bound to … /tasks unbind first`. `/help vk` shows the `/tasks` syntax.
- `/reopen <unit>` (any map) returns a done or dropped unit to To do.
